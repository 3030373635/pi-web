# 全站 Chrome 103 兼容验收

沿用已授权的独立兼容层方案及临时分支。用户明确要求将此前未覆盖的页面与主要交互补齐，验证继续全部在 Windows GitHub Actions 执行，不在本地运行测试或生产构建，不合并主分支。

验收范围按真实产品入口划分，而非只计算 Next 路由（项目只有 `/` 和 `/login`）：

1. 登录表单与失败、重试、成功跳转。
2. 聊天滚动、输入草稿、模型/思考/工具选择、新会话、会话导航/分支/搜索/菜单。
3. Markdown、工具、思考、数学、SVG、Mermaid、代码与常见文件预览，及 zoom/source 等交互。
4. General、Models、Skills、Sub-agents、Plugins、MCP 的主要配置操作和弹窗；需要验证提交数据，不能以非空或加载提示当作成功。
5. 终端、子代理查看、系统提示/工具定义、扩展 UI、Debug、项目/工作树入口。
6. 独立记录 Windows 服务集成、真实浏览器+受控模拟接口、无法在 hosted runner 证明的能力（真实第三方 OAuth、模型推理、系统原生 PDF 组件、Win10 1909 实机）。

比较过的方式：只扩展截图会遗漏交互及异步 chunk；依靠真实第三方服务会依赖凭据并改动外部状态。因此保留真实组件与浏览器，界面配置流程使用受控服务，导航/本地文件等尽量直接使用隔离服务。设置、内容、平台各自模块与矩阵任务，互不阻断，复用同一生产构建。

CI 对每一验证生成覆盖记录（id、实际操作、服务类型、浏览器与构建模式）及截图/trace，成功结论只针对记录中的验收项，不能描述为无限制的全部交互穷举。
